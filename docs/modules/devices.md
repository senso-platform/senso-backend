# devices

Шлюзы и устройства: реестр, владелец, жизненный цикл и наблюдения связности. Схема БД `devices`.
Разрешённые зависимости: `identity::api`, инфраструктура `shared`. Реализация находится в `internal`,
публичные DTO и `DeviceQueries` — в именованном интерфейсе `api`.

## Модель и хранение

- `Gateway`: UUIDv7, UUID владельца, внешний MQTT-id, имя, BCrypt(12)-хэш MQTT-пароля, состояние
  `UNKNOWN / ONLINE / DEGRADED / OFFLINE`, текущий `bootId`, время последнего статуса и inventory.
- `Device`: UUIDv7, UUID шлюза, внешний id, тип, имя, capabilities и metadata в JSONB,
  статус `PENDING / ACTIVE / REJECTED / DISABLED`, независимая связность `UNKNOWN / ONLINE / OFFLINE`,
  время реального наблюдения и аудит подтверждения. Capabilities — value records, отдельной таблицы нет.
- Уникальность устройства — `(gateway_id, external_id)`. Одинаковые внешние id на разных шлюзах допустимы.
- FK существуют только внутри схемы `devices`; владелец и подтвердивший пользователь — логические UUID.
- `processed_messages` хранит `(gateway_id, message_id)` для discovery и inventory. Запись отметки и
  изменения устройств атомарны. При откате отметка тоже откатывается.
- Новая миграция: `V202611051200__devices_registry.sql`; прежние миграции не меняются.

## Сервисы

`GatewayService.create(ownerId, name)` проверяет существование пользователя через `IdentityApi`, генерирует
внешний id и криптографически случайный MQTT-пароль. Пароль возвращается только в результате создания;
его `toString()` скрывает секрет. Сохранённый шлюз и `GatewayView` сырой пароль не содержат.
Также доступны получение, переименование и список шлюзов владельца.

`DeviceService` предоставляет получение, переименование, список, approve/reject/disable/enable.
Переходы соответствуют ADR: `PENDING → ACTIVE`, `PENDING → REJECTED`, `ACTIVE → DISABLED`,
`DISABLED → ACTIVE`. Новое discovery может вернуть `REJECTED → PENDING`; повтор старого сообщения этого
не делает. Повтор той же пользовательской команды идемпотентен. Подтверждение запоминает актора и время;
последующие disable/enable не переписывают аудит.

Проверка владельца выполняется сервисами. Чужой объект возвращает `NotFoundException`.
`ownerId` — доверенный параметр внутреннего вызова: будущий HTTP-адаптер обязан получать его из JWT,
а не из тела запроса. HTTP-адаптер сейчас отсутствует.

Списки используют `PageRequestParams.fetchSize()` и `CursorPage.of` с порядком `(created_at DESC, id DESC)`.
Курсор не заменяет фильтр владельца. Можно ограничить список устройств конкретным шлюзом владельца.
Маппинг сущностей в DTO выполняет Spring MapStruct `DeviceMapper`.

## Публичный API для модулей

`DeviceQueries`:

- `resolve(gatewayExternalId, deviceExternalId)` — доверенный worker lookup, возвращает только `ACTIVE`;
- `find(ownerId, deviceId)` — получение с проверкой владельца;
- `list(ownerId, gatewayId, params)` — ограниченный курсором список владельца.

`resolve` позволяет будущему telemetry отбрасывать неизвестные и неподтверждённые устройства. Саму запись
телеметрии этот модуль не реализует. `alerts` и `realtime` могут зависеть только от `devices.api`.

## Наблюдения от шлюза

`DeviceDiscoveryService` принимает существующие payload records из `messaging-contracts` после проверки
JSON Schema. Это сервис приложения без MQTT/AMQP-listener; он не является готовым транспортным endpoint.

- Discovery создаёт `PENDING`, обновляет сведения и наблюдаемую связность существующего устройства.
  `ACTIVE` и `DISABLED` при повторном обнаружении сохраняются.
- Inventory — полный снимок: отсутствующие устройства получают `OFFLINE`; metadata сохраняется, поскольку
  формат inventory её не передаёт. Устаревший снимок игнорируется. Запоздавшее discovery до последнего
  inventory не создаёт ложное подключение, включая ранее неизвестный id.
- Не более 50 `PENDING` на шлюз. Превышение даёт `ConflictException` и откатывает весь снимок вместе с отметкой
  обработки. Будущий listener должен применять общую политику retry/DLQ из AGENTS, а не подтверждать ошибку.
- Все изменения сериализуются блокировкой строки шлюза: конкурентные discovery, inventory и команды
  владельца не нарушают уникальность, лимит или аудит.
- Статусы шлюза не проходят дедупликацию по messageId. `OFFLINE` применяется только к `bootId` последнего
  `ONLINE`; статический `sentAt` Last Will не сравнивается со временем heartbeat. Устаревший Will другой
  сессии игнорируется. При доставке `DEGRADED` раньше более старого `ONLINE` актуальное состояние сохраняется;
  поздний `ONLINE` только подтверждает сессию для Last Will. Повторное подключение отражается новым `ONLINE`.
- Метрика `devices.observations` (`devices_observations_total` в Prometheus): `operation`, `result`.
  Это счётчик обработки; он не является транзакционным аудитом. Создание шлюза и изменения статуса устройства
  логируются с MDC-идентификаторами без секретов.

## Контракты и оставшиеся зависимости

Сабмодуль `contracts/` доступен; при реализации использован commit `6269c24`. README называет его источником
истины, пометки draft нет; факт согласования с C++-командой локальными файлами не подтверждается.
Использованы MQTT v1: envelope (`messageId`, `gatewayId`, `bootId`, `sentAt`) и payloads
`DEVICE_DISCOVERED`, `DEVICE_INVENTORY`, `GATEWAY_STATUS`. Форматы и DTO контрактов не менялись.

Текущий OpenAPI содержит только auth, users/me и временный debug endpoint. Следующий PR должен:

1. Согласовать в `senso-contracts` REST шлюзов/устройств и MQTT auth, сгенерировать интерфейсы и добавить
   `@ApiRole`-контроллеры с JWT и негативными HTTP-тестами. Реализация `CurrentUserId` и security filter chain
   пока отсутствуют; внутренние сервисы не заменяют аутентификацию.
2. Реализовать готовящийся pipeline ingest и подключить существующий `ValidatedMessageV1` через
   `q.devices.inbound`: валидация, topology, роли, заголовки, три повтора, DLQ, ack только после коммита.
   В текущем ingest нет приёма/валидации/публикации; несовместимый временный транспорт не добавлялся.
3. Подключить через Modulith outbox согласованные события для realtime. Сейчас брокерные уведомления
   и SSE не публикуются.
4. Добавить worker-пересчёт связности по таймауту/телеметрии под ShedLock. Сейчас связность отражает
   discovery/inventory и явные статусы шлюза; период измерений в контракте не задан.
5. Определить срок хранения и очистку `devices.processed_messages`, согласовать каталог типов и единиц
   с C++-командой. Добавить ротацию/отзыв MQTT-паролей вместе с готовым broker auth backend.

`docs/bootstrap/INIT-PLAN.md`, упомянутый в правилах, в checkout отсутствует; скелет Maven уже собран.
Новые библиотеки, инфраструктура и зависимости между модулями не добавлялись.

## Проверки

Unit-тесты покрывают доменную модель, Last Will, MapStruct, владение, курсоры, секреты и статусы.
`DevicesIT` использует `@ApplicationModuleTest(DIRECT_DEPENDENCIES)` и общий `IntegrationTestBase`:
настоящие TimescaleDB/PostgreSQL и RabbitMQ. Брокер запускается общей инфраструктурой; доставка AMQP пока
не проверяется. Проверяются JSONB, миграция, scoped discovery, approval,
скрытие чужих объектов, inventory, запоздавшие сообщения, дедупликация, её откат, лимит и конкурентные дубли.
Общие тесты контекста продолжают проверять роли api/worker/local.

Фактические результаты сборки и полный список файлов: [отчёт реализации](devices-implementation-report.md).
